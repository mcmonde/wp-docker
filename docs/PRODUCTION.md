# Production deployment guide

Use this checklist when moving from local development to a public server. For day-to-day configuration, see [USAGE.md](USAGE.md).

---

## Architecture summary

Only **Nginx** publishes ports to the host:

| Port | Service | Public? |
|---|---|---|
| **80** | Nginx (HTTP + ACME) | Yes |
| **443** | Nginx (HTTPS, after `./enable-ssl.sh`) | Yes |
| 9000 | PHP-FPM | No — internal only |
| 3306 | MariaDB | No — internal only |
| 6379 | Redis | No — internal only |
| 8080 | phpMyAdmin | No — `127.0.0.1` only when `--profile tools` |

All WordPress instances share Nginx, MariaDB, and Redis. Each instance has its own PHP container, database, and `sites/<id>/wp-content/`.

## Pre-launch checklist

### DNS and URLs

- [ ] `DOMAIN` in `sites/<id>.env` matches your public hostname.
- [ ] `WP_HOME` is the full production URL (`https://example.com`).
- [ ] DNS A/AAAA records point to this server.
- [ ] Remove or disable dev-only instances (`localhost`, `*.localhost`) unless you need them behind a hosts file.

### TLS

- [ ] Set a real `EMAIL` in `.env`.
- [ ] Port **80** is reachable from the internet (required for Let's Encrypt).
- [ ] Run `./enable-ssl.sh` for each public instance.
- [ ] Confirm `./up.sh` publishes **443** (`COMPOSE_FILE` includes `docker-compose.ssl.yml`).

### Host firewall

Docker binds ports before UFW rules, so configure the **host** firewall:

```bash
ufw allow OpenSSH
ufw allow 80/tcp
ufw allow 443/tcp
ufw enable
ufw status
```

Do **not** expose `3306`, `6379`, `8080`, or `9000` publicly.

Include **IPv6** if Docker publishes `[::]:80` and `[::]:443`.

### Server sizing

- [ ] The server has capacity for every instance: 1 vCPU and 2 GB for the first, plus 0.5 vCPU and 512 MB per extra weight-1 instance. `./generate-env.sh` refuses otherwise; do not use `FORCE_SITES=yes` in production. See [Site capacity](../README.md#site-capacity).
- [ ] Swap is configured (2 GB on a 2 GB server, 1–2 GB on larger ones) so a burst does not get MariaDB killed.
- [ ] `ALLOCATE_RESOURCES=yes` if one busy instance must not starve the others.
- [ ] `PHP_WORKER_AVG_MB` matches real worker memory (120+ for WooCommerce or page builders).
- [ ] After resizing the server, run `./generate-env.sh && ./up.sh` to re-tune.

### Media storage

- [ ] Decide whether uploads stay on the server (`sites/<id>/wp-content/uploads/`, include them in file backups) or go to DigitalOcean Spaces ([SPACES.md](SPACES.md)).
- [ ] If using Spaces: real credentials in `sites/<id>.env`, CDN enabled if `SPACES_PUBLIC_URL` uses the CDN host, and existing uploads moved with `./migrate-spaces.sh`.

### Secrets

- [ ] `.env` and `sites/*.env` are mode `600` and never committed.
- [ ] `MYSQL_ROOT_PASSWORD` and `REDIS_PASSWORD` in `.env` are strong (auto-generated by `./generate-env.sh`).
- [ ] Each site has its own `DB_PASSWORD` and WordPress keys in `sites/<id>.env`.

### Services to avoid on production

- [ ] Do **not** run `docker compose --profile tools up -d` (phpMyAdmin) unless required.
- [ ] If you need phpMyAdmin, keep it on `127.0.0.1:8080` and use an SSH tunnel:

```bash
ssh -L 8080:127.0.0.1:8080 user@your-server
```

### Backups

- [ ] `./backup.sh` works and files appear in `backups/`.
- [ ] Daily cron exists (installed by `./generate-env.sh` at 03:00).
- [ ] Test `./restore.sh` once.
- [ ] Copy backups and `sites/*/wp-content/` off the server.

### WordPress hardening (built in)

This stack already sets:

- `DISALLOW_FILE_EDIT=true` — no theme/plugin editor in admin.
- Nginx denies `xmlrpc.php`, `wp-config.php`, and dotfiles.
- Security headers on every vhost (see below).
- Rate limit on `wp-login.php` (10 requests/minute per IP, burst 5).
- Redis authentication (`REDIS_PASSWORD` in `.env`, `WP_REDIS_PASSWORD` in each instance).
- Per-instance Redis database index and key prefix.

## Security headers (Nginx)

Every HTTP and HTTPS vhost includes:

| Header | Value |
|---|---|
| `X-Frame-Options` | `SAMEORIGIN` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` |

HTTPS vhosts also send:

| Header | Value |
|---|---|
| `Strict-Transport-Security` | `max-age=31536000` |

Regenerated by `./generate-env.sh` into `nginx/conf.d/<id>.conf`.

## Redis password

Redis requires a password (`REDIS_PASSWORD` in `.env`). WordPress receives it as `WP_REDIS_PASSWORD` via `WORDPRESS_CONFIG_EXTRA`.

After changing the password:

```bash
./generate-env.sh
./up.sh
docker compose exec -T -u "${PUID}:${PGID}" <site_id> wp cache flush
```

## Logging and debugging

### Nginx (per instance) — primary web logs

Mounted to the host at `nginx/logs/`:

| File | Contents |
|---|---|
| `nginx/logs/<id>.access.log` | HTTP requests for that instance |
| `nginx/logs/<id>.error.log` | Nginx errors for that vhost (502, upstream timeouts, etc.) |
| `nginx/logs/error.log` | Global Nginx errors |
| `nginx/logs/access.log` | Global access log (if used) |

```bash
tail -f nginx/logs/blog.error.log
tail -f nginx/logs/blog.access.log
```

### Docker container logs (PHP-FPM / stdout)

PHP-FPM and the container entrypoint log to Docker's logging driver:

```bash
docker compose logs -f blog
docker compose logs -f default
docker compose logs -f nginx
docker compose logs -f redis
docker compose logs -f db
```

Use this for PHP fatal errors, FPM warnings, and startup issues.

### WordPress `debug.log` (optional, not enabled by default)

WordPress does **not** write `debug.log` unless debugging is turned on. To enable for one instance, add to `generate-env.sh` `WORDPRESS_CONFIG_EXTRA` or extend it per site:

```php
define('WP_DEBUG', true);
define('WP_DEBUG_LOG', true);
define('WP_DEBUG_DISPLAY', false);
```

Then regenerate and restart. Logs appear at:

```text
sites/<id>/wp-content/debug.log
```

Disable debugging in production when you are finished troubleshooting.

### MariaDB

```bash
docker compose logs -f db
```

### Quick “where do I look?” table

| Symptom | Check first |
|---|---|
| 502 / blank page | `nginx/logs/<id>.error.log`, then `docker compose logs <id>` |
| Login / redirect issues | `nginx/logs/<id>.access.log` |
| Plugin / PHP error | `docker compose logs <id>` or enable `WP_DEBUG_LOG` |
| Slow queries | `docker compose logs db` |
| Cache oddities | `docker compose logs redis`, then `wp cache flush` |

## Go-live commands

```bash
# 1. Configure each public site
#    sites/<id>.env → DOMAIN, WP_HOME=https://...

# 2. Regenerate and start
./generate-env.sh
./up.sh

# 3. Enable TLS
./enable-ssl.sh

# 4. Verify
curl -sI https://your-domain.com | grep -E 'HTTP/|strict-transport|x-frame'
docker compose ps
```

## Behind Cloudflare or another proxy

If TLS terminates at the proxy:

- Leave instances on HTTP at the origin, or use Full (strict) with origin certificates.
- Restrict origin firewall to proxy IP ranges when possible.
- Do not skip `./enable-ssl.sh` if the origin should speak HTTPS to the proxy.

## Ongoing operations

| Task | Command |
|---|---|
| Backup now | `./backup.sh` |
| Restore | `./restore.sh` |
| Renew TLS | Automatic via `renew-ssl.sh` cron (04:15) |
| Update WordPress core | `./backup.sh` then `./upgrade-wordpress.sh` |
| Change URL | `./change-url.sh <id> <old> <new>` |
| Reload Nginx after manual cert renewal | `docker compose exec -T nginx nginx -s reload` |

## Recommended host hardening (outside this repo)

- SSH key authentication only; disable root login.
- Fail2ban or similar for SSH and optionally Nginx (`wp-login.php` rate limit is already in Nginx).
- Unattended security updates for the host OS.
- Monitor disk space (`db_data` volume, `backups/`, `sites/*/wp-content/uploads/`).
